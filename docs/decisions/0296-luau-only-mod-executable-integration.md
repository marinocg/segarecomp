# ADR 0296: a Luau-only mod in the generated-native executable path

- Status: accepted (SEG-137-T007, combined delivery F07). Builds on [ADR 0294](0294-luau-vendoring-vm-and-trusted-compile.md) (trusted compile), [ADR 0295](0295-luau-host-api-static-check-and-fixture-session.md) (the API), [ADR 0267](0267-genesis-native-compat-provider.md)-style overlay seam (the fixed HUD overlay path) and the launcher's executable cache.
- Scope (T007 as refined before F07): the single-mod, Luau-only, read-only case. Not the shared phase scheduler (SEG-138-T001), guest hooks, WRAM access, multi-mod composition, save-state of mod state, or a native ABI 2 provider runtime.

## Decision

1. **`segarecomp build --luau-package <p.segapatch> --luau-identity <id>`** (Genesis viewer builds). `--rom` stays the ORIGINAL image. The build re-verifies everything itself (a preview in the launcher is never trusted): the package reads as schema 3 and its identity is the one selected; `luau::live_support` (Genesis, Luau-only trust class, no native ABI, only the capabilities the live path grants); the original image is one the package declares; the effective image is derived by the package's own typed edits / guest code / BPS (`mod::effective_image`, which now also returns the bytes) and written to `<output>/input/effective.rom`, which replaces `--rom` for the rest of the build and is removed when the build ends (derivative data never outlives it); the scripts pass the static API check and compile in the bounded child (`luau_build.cpp`, shared with `mod build`). A refusal is a typed class (`E_LIVE_PLATFORM|TRUST|ABI|CAPABILITY`, `LUAU_PACKAGE_INVALID`, `LUAU_IDENTITY_CHANGED`, `LUAU_IMAGE_MISMATCH`, `E_LUAU_*`) in `status.json`; nothing is built or published. More than one package, a native patch beside it, Master System or a headless build are usage errors.
2. **The result is linked into the program, not stored beside it.** The build writes the stored compiled form (`luau_stored.cpp`) as constants (`luau/luau_artifact.c`: artifact bytes, package identity, bytecode digest, granted capabilities, the package's own limits) and compiles them with the Luau VM, the host API and one provider into the SAME generated-native program, so the executable cache entry IS the program and the artifact cannot be replaced after the build. At startup the program calls `load_stored(identity, bytes, digest)`, the same strict reader and digest check `verify_compiled` uses, before the VM sees a byte; nothing in a package is ever handed to `luau_load`.
3. **Live capabilities: `host.log` and `overlay.rgba`.** `frame.work_ram` needs a published frame copy that the live path does not provide (WRAM access is a non-goal), so a package that REQUIRES it is refused (`E_LIVE_CAPABILITY`) rather than run with a binding that returns nothing; an optional one is not granted. `sega.frame.value` therefore exists only in the diagnostic fixture session. The callbacks are `reset()` once and `render(frame)` once per presented frame, `frame` being the count of presented frames (0-based). The HUD example and the `luau` template for Genesis declare only the two live capabilities.
4. **The seam is the existing HUD overlay path.** `platforms/genesis/viewer/luau_provider.cpp` implements the ABI 1 `GenesisNativeCompat` table that the viewer already drives (`segarecomp_patch_provider`, `GENESIS_COMPAT_HUD` only, capability constant 8): for each presented frame the viewer calls `prepare`, the provider runs `render(frame)`, rasterizes the overlay requests (`luau::rasterize_overlay`, 128x256 RGBA8) and `hud` hands the image to the viewer, which composites it after the picture. No scenery, no frame data. This is not a scheduler: one call per frame, no phases, input, hooks or ordering.
5. **Failure isolation.** A fault (error, budget, memory, capability, range, ...) disables the mod for the rest of the session: one `LUAU_MOD_FAULT {...}` line (cause, mod, callback, frame) is written, every later frame is presented without an overlay, and the guest runs on unchanged to its own end. A VM that cannot be created or an artifact that does not verify declines every frame the same way (`LUAU_MOD_REFUSED`). Nothing here can stop the guest.
6. **Build toolchain.** The VM compiles as C++20 with exceptions (script errors use them) and the program is linked with the C++ driver (`options.cxx`, derived from the C driver as for ymfm), whose runtime defines `operator new`; the C-driver shim of the YM2612 (`ym-shim`) is therefore removed from the FINAL link of a Luau program only (the build's own pass-program links still use it). The Luau sources compiled are the VM (minus the libraries the policy does not allow), `luau_vm.cpp`, `luau_api.cpp` (API table, overlay raster; reuses the viewer's body font), `luau_stored.cpp` and `sha256.cpp`; the compiler, the static check and the media package reader are NOT linked into a game. `libs/luau_host` was split for this (`luau_stored.cpp` without compiler, `luau_config.cpp` for the media-dependent parts). The packaging install rules stage these sources next to the runtime.
7. **Executable cache (launcher).** One cache, the existing `entry_dir` / `entry_ready_for` / `BuildJob` / directory-rename publication. `RomView` gains a mod variant (`luau_identity`, installed package path, effective image digest, compiler pin; `select_luau_mod` verifies and fills it, refusing in plain language). The key gains `|luau=<package identity>:<effective image digest>:luau-<pin>` only when a mod is selected; the package identity names every payload digest, the capabilities and the ABI, and the pin with the fixed compile options determines the bytecode, so the bytecode digest is covered; the build's recorded bytecode digest is also stored in the entry record and `entry_ready_for` accepts an entry only for exactly the variant it records. Vanilla and schema 1/2 keys are byte-for-byte what they were (no segment is added without a mod; a test pins that stray mod fields change nothing). A mod's saves live in their own folder (`saves/genesis/<sha>/mods/<identity>`) and `SEGARECOMP_SAVE_VARIANT` is the package identity. The F03 variant metadata record (`<library>/cache/variants`) stays metadata: it is neither read nor reported as the executable.
8. **Test automation seam.** `SEGARECOMP_VIEWER_FINAL_FRAME=<file.bmp>` makes the viewer program save the last presented frame as composed for the window (picture and HUD overlay, no menus) when the run ends. It reads nothing from the guest and changes nothing it does.
9. **The synthetic `mod session` stays** as an isolated diagnostic tool (its output says so: `"synthetic_picture":true`); it is not the T007 proof.

## Evidence

`tests/mod_luau_executable_test.py` builds a runnable fabricated Genesis ROM (`platforms/genesis/sdk/examples/luau-hud/fixture_rom.py`, written for this repository) once Vanilla and once with the example package, runs both under the real SDL3 viewer (dummy drivers, `--instruction-budget`, timeouts) and checks: identity and bytecode digest agree across `mod build`, `status.json` and the running program; the frames differ only inside the HUD region, the HUD pixels equal an independent derivation from the Vanilla frame, the crop hash is pinned; two runs are byte-identical; a changed script gives another identity, digest and frame; a script fault disables only the mod and the program ends on the exact Vanilla frame at the same guest stop; every unsupported combination is refused with a typed class and no executable. `launcher_mod_variant_test` drives the real `BuildJob` and the real build driver (the bundled Zig is a thin wrapper around the host compiler) through the launcher cache: key components, reuse, invalidation by script/image/pin, no cross-acceptance between Vanilla, mods and schema 1/2, a failed build that publishes nothing and leaves every other entry byte-identical. The existing schema 1/2 provider build and viewer tests pass unchanged.

## Limitations

- Linux only for the generated-native tests (as `genesis_patch_provider_build_test`); the Windows and macOS builds of such a program are not exercised by CI.
- The launcher UI has no screen to select a mod version (non-goal); `select_luau_mod` is the seam it will call.
- No frame data, input, guest memory, hooks or multi-mod ordering (F08-F19). The frame argument counts presented frames, not guest VBlanks.
- Optimized AOT (`--aot-policy optimized`) with a mod is not covered by a test.
- The Luau VM adds about 60 source files to every Luau-mod build; Vanilla builds are unchanged.
