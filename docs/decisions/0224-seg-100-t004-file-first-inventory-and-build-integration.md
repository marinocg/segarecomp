# ADR 0224: SEG-100-T004 - file-first candidate inventory and integration into the supported build

- Status: Accepted. Milestone SEG-100 (M4). Related: ADR 0221 (architecture, feasibility), 0222 (bodies), 0223 (binding), 0205 (the self-service build), 0214 (inventory status).
- Privacy: project-authored fixtures; for the authentic discs, classes and counts only.

## Candidate enumeration (one reader, no authority from names)

`enumerate_file_candidates` (platforms/sega-cd/machine/src/file_candidates.cpp) walks the ISO9660 volume of the disc's first data track with the one reader of `libs/media` (breadth-first, directory order: deterministic; at most 4,096 entries; any reader error is a typed failure and `file_candidate_error` stops the build - a disc with no usable volume, or a volume the reader rejects, is **never** an empty or guessed inventory). It consults no name, extension, path, address or title. Raw executable extents of a disc without an ISO9660 volume remain outside this producer (explicitly incomplete); the execution-derived and static producers keep covering them.

## Policies

`segarecomp sega-cd emit|build --file-first all|structural [--file-first-max-bytes N] [--file-first-max-offsets N]`. Bodies are compiled for a **dynamic image** per admitted file (ADR 0222, 0223).

- `all`: every even offset of every candidate file the CPU owner decodes and lowers.
- `structural` (the policy with a measured coverage argument, ADR 0221): only offsets whose forward flow is closed and decodable under the CPU owner's own decode and control rules (`structural_closure`): an offset is valid when an instruction decodes there and every fixed successor that stays inside the file (the fall-through of a non-terminating instruction, a PC-relative branch/call/`DBcc` target) is itself valid. Absolute targets, computed transfers, returns and the continuation a call stacks are boundaries - they neither validate nor invalidate (a call with inline data after it stays valid). A decode failure, a PC-relative target outside the file or on an odd address, an always-faulting instruction and a fall-through off the end of the file invalidate everything that depends on them. It is the greatest fixed point, so loops are valid; it has no threshold, density or name. It is **only a build-time compile filter**: not executable authority, not a completeness argument.

A candidate must be wholly resident in one processor's executable RAM to be bound as one image, so files larger than 512 KiB (`--file-first-max-bytes`, at most `0x80000`) are not candidates. **That is a typed incompleteness, not a silent exclusion**: the report counts `oversize_files` and bytes, and `complete:false` makes the inventory name `file_first_inventory_incomplete`. Likewise `unreadable_files`, `over_budget_files` (with `--file-first-max-offsets`, files are admitted by descending structural density, ties by block, until the budget is full) and `duplicate_files` (identical bytes are one image: an indistinguishable candidate would be an ambiguity by construction) are counted. `no_structure_files` and `empty_files` are listed. The policy never claims a complete executable inventory: `status.json` always names `file_first_runtime_binding` and, for `structural`, `file_first_structural_filter`.

## Product integration (reuse; nothing replaced)

- The BIOS-image profile's emitter takes the images as `BiosProfileInputs::dynamic_images`; the program identity gains a `dynamic.v1` line (policy, each image's track offset, SHA-256 and candidate mask) **only when images are present**, so every existing build keeps its identity. The images are verified against the disc when the program is built (`digest_mismatch`), duplicated content is refused, and the disc identity is verified again by the runtime at start-up.
- Bodies are partitioned into 1,024-body translation units (`d_b<N>.c`) and one map unit per image (`d_m<N>.c`); their text depends only on the image set and the policy, never on the round or the admissions, so **every round of the build reuses their objects** (the existing compiler cache keys units by text). The units are generated by up to 16 worker threads, deterministically (the same text whatever the worker count - tested).
- The static (execution-derived and static-scan) producers and the overlay machinery are unchanged and keep precedence: a PC they own is dispatched by their `case`; only a PC no static `case` owns reaches the binder. With `--file-first` a module is therefore compiled before any run and the build pass does not need to resolve its extent; the extent producers remain the fallback for everything the dynamic images do not explain.
- `status.json` gains `file_first` (policy, identity, file accounting, compiled inventory, shared-body statistics, text sizes) next to the unchanged `aot_policy`; the run report gains a `dynamic` section (ADR 0223). Compatibility, the experimental M3+B35 selector (never an image authority here) and the Genesis/Master System paths are untouched.

## Resource controls

Bounds are typed, never silent: 4,096 directory entries; 512 KiB per image; 256 MiB of candidate files held while selecting (the rest are `over_budget_files`); 4,096 images; 32 Mi candidate offsets in one emission (`too_many_candidates`: use `structural` or an offset budget); an optional candidate-offset budget; 16 bindings per processor; 64 anchor occurrences per search; the unchanged state/step bounds of the other producers. The measured costs are in ADR 0221 (census) and ADR 0225 (builds).
