# ADR 0254: SEG-110 (M14) - the Earthworm Jim SE executable-code frontier is a relocated fragment; derived-image feasibility

- Status: Accepted. Milestone SEG-110 (M14). Related: ADR 0142 (verified broad AOT, bounded image materialization), 0205 (reference-independent extent discovery), 0220 (authentic loader discovery), 0221 (file-first AOT), 0223 (dynamic source-to-RAM binding), 0225 (authentic evaluation).
- Privacy: processor, memory class, counts, sizes and times only. No address, disc offset, LBA, hash, file name or byte of a disc, BIOS or backup RAM appears here. The authentic runs and the derived extent are local and ephemeral.
- Decision: **`M14_DERIVED_IMAGE_FEASIBLE`** - but the frontier is not a derived (decompressed, decoded or generated) image. It is a short relocated fragment of an already-verified image, and the missing piece is a provenance-qualified identity rule, not a producer.

## 1. Authentic frontier, reproduced (T001)

Operator's legally held Earthworm Jim SE (USA) disc, Model 1 (USA) BIOS, empty backup RAM, no module list, extent, entry, manifest, patch or Z80 workaround. `segarecomp sega-cd build`, current `main` (after M13).

| arm | rounds | build wall / CPU / peak child memory | program | run | stop |
|---|---|---|---|---|---|
| Compatibility (reference) | 6 | 138 s wall / 565 CPU-s / 540 MiB at 16 jobs | 42.5 MB | 5.7 s, 28,418,828 instructions | `entry_not_compiled`, main Work RAM, refusal `no_source` |
| `--file-first structural` | 6 | 177 s wall / 996 CPU-s / 590 MiB | 85 MB | 8.4 s, 28,418,828 instructions | the same, same instruction, same cycle |

The two complete run reports are equal in every machine-state field (registers, retired counts, trace hashes, memory digests, device log, frame digest, stop); the executed instruction starts are identical (main 1,577, sub 3,637). File-first compiled 107 disc-file images (200 files, 13.5 MB, 328,894 offsets, 34,132 bodies) and bound **0** of them: no disc-file instruction runs before the frontier. Delivery ledger: complete (not overflowed), 56 sectors from the start of track 1. Admitted before the stop: two boot-area extents (one per processor) and 78 operand templates. Static loader scan: `destination_unknown`, unchanged (independent). The frontier is identical in both modes, so the stop is not a file-first omission.

## 2. Where the executable bytes came from (T002)

Method: the generated program's existing local `--ram-write-log` (RAM writes with the writer's program counter) and `--dump-dir`; no new runtime tracing.

- **The stopped instruction is the first byte of a 21-byte write stream into main Work RAM** - ascending, contiguous, one writer program counter, the very last RAM writes of the run before the jump. The 64-byte neighbourhood around it is an unrelated data buffer (written by graphics/data loops over the whole boot), which is why "about half of the surrounding blocks are verbatim file bytes".
- **The writer is a byte-copy loop inside the admitted boot image (the initial program)**; its source address, destination address and count are immediate operands of the verified code.
- **The stream is a verbatim copy of a position-independent fragment of that same image**: 20 bytes of code (an address-register move, a long-copy loop, a Gate Array write, a wait loop, an indirect jump) plus one overshoot byte. It occurs exactly once in the delivered blocks (and once in a raw scan of the whole image).
- The fragment is a trampoline: it copies a 48 KiB stage from Word RAM over the initial program (that is why it cannot run in place) and jumps back. With the 20 bytes admitted, the existing discovery admits the next 48 KiB as an **exact copy of one delivered disc span** (the next round) and the program continues for ~43,000 more main instructions to a different, typed stop.

Hypotheses: **A** (copy with header/patches) - no, the source is an unpatched run of 21 bytes; **B** (relocation of an immutable body) - **yes**, within one verified image, to a different RAM address; **C** (decompression) - no: the writer is a plain byte copy and the written values equal the source; **D** (XOR/delta) - no, same reason; **E** (code generated by instructions) - no: no value is computed; **F** (source present on disc but excluded) - partly: the source is the boot area, which is an admitted static extent but not an ISO9660 file candidate and not an exact-copy run of 32/64 bytes; **G** (loader/source-resolution problem) - **yes: the exact-copy resolver's identity floors** (32-byte anchor at the PC, 64-byte run, ADR 0205/0223) cannot accept a 20-byte fragment, whatever follows it in RAM. `no_source` does not mean "transformed": it means "no delivered run of at least 64 bytes explains the window".

Whether another route or input affects it: the fragment is produced by boot code before any pad input and is identical in the two modes and in all repeated builds. Capture epoch: the first instruction fetch from the stream (the same stop the build pass already uses). Production is deterministic: identical write stream, identical program identity across builds at 4 and 16 jobs.

Next typed stop with the fragment (and the following 48 KiB exact copy) admitted: **`main_device_unsupported`, a one-byte read by the main processor of the Z80 address window**, from the second stage - not an executable-image problem; unchanged between Compatibility and file-first (identical machine state, 13,197,846 main instructions).

## 3. Mechanisms compared (T003)

| | authority | proof the compiled bytes are the executed bytes | if the output changes | variants / overlays | build cost and bounds | generality |
|---|---|---|---|---|---|---|
| **1. Static producer reconstruction** (constant-propagate the copy loop's operands over the verified image) | verified image + proven loop semantics | the same per-instruction guard | the static proof fails -> typed refusal | needs a loop/idiom prover; every new idiom is a new proof | cheap to run, but the loader scan already stops at `destination_unknown` for this very boot | covers only idioms it models |
| **2. Offline bounded materialization** (derive the fragment from the pass's *observed* write stream and admit it as an ordinary extent) | a verified writer + a unique delivered source + the observed stream; execution authority stays the per-instruction byte guard | `extent:` admission validated by the emitter against the pass identity, the disc digest and the processor's RAM; every body begins with `scd_code_guard` | a changed byte fails the guard (`code_bytes_mismatch`), a changed disc fails the start-up digest | extents at one address coexist as variants, newest first (existing behaviour) | one extra build round; stream <= 4 KiB; no new emitter or engine | any relocated fragment in main Work RAM / sub PRG RAM; Word RAM and Z80 RAM need write evidence the log does not carry |
| **3. Source-relative reuse** (lower the dynamic binder's 64-byte floor and allow admitted images as sources) | byte equality of a short run | the guard | the binding is skipped | existing | adds a runtime search with 20-byte anchors: ambiguity and false identities rise sharply (the 20-byte string is unique here, but 32 bytes of common M68K prologues are not) | none beyond equality |

**Recommendation: mechanism 2**, derived at build time from the pass, not mechanism 3. It reuses the existing image-authority model (extent admission), the C11 emitter, the byte guards and the discovery loop; it adds no runtime machinery. The producer's logic (stream evidence) stays separate from instruction lowering. Because every executed instruction is compared with the admitted (disc-verified) bytes, a wrong derivation cannot execute wrong code; its worst case is a typed stop or wasted compile - which is exactly why the derivation needs the stream and the unique source: to keep the answer single and explainable, not to make execution safe. Equality alone is not accepted as classification (ADR 0178 policy): a window explained only by a coincidental run is not claimed.

## 4. Project-authored proof (T004)

`tools/sega_cd_bios_loader_fixture.py` cases `relocated`, `relocated_short`, `relocated_patched`, `relocated_duplicate` (a loaded module copies a 24-byte fragment of its own admitted image to PRG RAM and runs it; the window after the fragment is not the source's) and the diagnostic `tools/sega_cd_relocation_provenance.py`, checked by `tests/sega_cd_derived_image_test.py` (19 checks, CTest `sega_cd_derived_image_test`):

- today's resolver refuses the fragment (`no_source`) and the program stops at its first instruction; the derivation gives an extent equal to the fixture's ground truth (used only to judge), the rebuilt program runs the fragment to its end, and repeated derivation/build give identical answers and program identity;
- wrong source -> `code_bytes_mismatch`, marker unchanged; a disc byte changed after admission -> `disc_identity_mismatch`, nothing executes; restored -> runs; a derived extent under another pass identity -> `provenance_mismatch`, under the right one it re-validates;
- incomplete output (16 of 24 bytes copied) -> the derived extent is the produced prefix and the program stops with a typed `entry_not_compiled` at the first byte never produced; a copy patched after production -> refused (`stream_overwritten`), and forced as an extent it still never executes (`code_bytes_mismatch`);
- two identical delivered sources -> `ambiguous_source`; a stream written by unadmitted code -> `writer_not_verified`; no ledger -> `no_delivery_evidence`; immediates computed by instructions (the existing `generated` case) -> refused.

The same tool run on the authentic disc's stopped run derives the extent that the manual experiment had used (processor, memory class, 20 bytes, one occurrence, no later overwrite) from write stream, verified writer and uniqueness alone; no game-specific constant is in the tool.

## 5. Authentic experiment with the derived extent (T005)

| arm (derived 20-byte extent via the existing testing hook `--emit-arg --disc-image`) | rounds | extents | build | program | result |
|---|---|---|---|---|---|
| Compatibility, 16 jobs | 7 | 2 boot + fragment + 48 KiB stage | 164 s wall (cache warm) | 47.5 MB (+5.0 MB) | `main_device_unsupported`, 28,418,828 -> 13,197,846 main / 15.3 M sub instructions |
| Compatibility, 4 jobs | 7 | same | 101 s wall / 104 CPU-s (warm) | byte-identical size, **identical program identity** | same |
| `--file-first structural` | 7 | same fragment; the stage extent is the 16 KiB exact-copy prefix the epoch showed | 196 s wall / 775 CPU-s | 87 MB | identical machine state to Compatibility, same stop |

The old `no_source` frontier is explained; the original generated-native program executes the resulting image through the guard; the next stop is a separate main-side Z80-window read. Costs: one build round, +5.0 MB for the 48 KiB stage that becomes reachable (the fragment itself is ~10 instructions); the derivation costs a second deterministic run (~6 s) and a bounded log (75 MB here; M15 should replace it with a bounded per-region stream table).

## 6. Limits and what is NOT claimed

- The extent is the **exact-copy run visible at the stop epoch**, not "everything the stage will ever execute": the file-first arm saw a 16 KiB prefix of the 48 KiB stage and was still machine-equal only because nothing beyond it ran before the stop. A later route stage may need another round (existing discovery behaviour).
- The stream check covers sub-processor and main Work RAM writes in the log; main-processor writes into PRG RAM are not streams (a changed value is still caught by comparing the stream with the live window). The M15 port must merge the delivery ledger exactly as `resolve-source` does (review finding, fixed in the diagnostic).
- Only main Work RAM and sub PRG RAM have write evidence. Word RAM relocation (a sub program copying its own module through Word RAM) and Z80 RAM uploads are not covered; they need their own evidence design.
- A second title was not available with this frontier class; generality is argued from the idiom (copy-and-run trampolines) and shown on the project fixture, not demonstrated on a second authentic disc.
- Playability is not claimed: the next stop is a Z80-window read; ADR 0225's separate developer-controlled Z80 experiments are unrelated to this mechanism.
- The static `destination_unknown` loader-scan refusal is unchanged and independent.

## 7. M15 scope (recommended)

One product PR: **provenance-qualified relocated-fragment admission in the build pass**. (1) Build-pass-only capture of the single write stream that owns the frontier PC (start, owned length, writer class, bounded 4 KiB) in `capture.json` instead of an unbounded log; (2) the derivation of `tools/sega_cd_relocation_provenance.py` implemented in the C++ build driver beside `resolve-source` (same refusal vocabulary, the diagnostic kept as the oracle for a differential test); (3) the result admitted as an ordinary `extent:` under the pass identity, nothing new in the emitter or runtime; (4) regression on the fixtures above plus the negative checks above; (5) authentic confirmation on this title ends at the Z80-window stop. Explicit non-goals: decompression/transform producers, Word RAM and Z80 evidence, changes to the dynamic binder's floors, the Z80 window itself.
