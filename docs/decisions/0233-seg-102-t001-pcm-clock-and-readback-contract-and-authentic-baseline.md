# ADR 0233: SEG-102-T001 - RF5C164 sample clock, running-pointer readback contract and the authentic baseline (M6)

- Status: Accepted. Milestone SEG-102 (M6), task T001. Gate `PCM_TIMING_FEASIBLE` (with the stated residual assumptions).
- Related: ADR 0144 (sub-side hardware), 0177 (BIOS-image timing, line-locked sub clock), 0223 (dynamic binding), 0225-0226 (M4), 0227-0232 (M5, in particular 0230 which diagnosed the two stops).
- Privacy: classes, counts, widths and hardware register offsets only. No BIOS or disc byte, hash, address, LBA, file name, frame image or trace, and no pointer value read from the commercial image, appears here. The reference emulator is a behavioural reference only: its source is consulted, none is copied, and its licence (non-commercial, source redistribution conditions) is not the project's.

## Question

The M5 frozen program stops with `pcm_unsupported` at two independent authentic reads of the PCM chip's wave-address pointers (ADR 0230). What exactly does the sub processor observe when it reads them, and what is the smallest deterministic mechanism that reproduces it, without producing sound?

## Two properties of the reference's host that matter (and are not copied)

1. **The shipped host resynchronizes every video frame.** In GPGX the PCM clock counter is reset to 0 by `pcm_update()` at the end of every audio frame, while the sub's cycle counter is also rebased; every read therefore runs `ceil(t / 1536)` events from the *frame start*. Measured on the reference with audio enabled (same authentic input-free run): **544 events per 834,208-cycle frame** against the exact 543.1, i.e. an effective rate of 32,605.8 Hz, **+0.165 %**: a channel's pointer drifts by one sample per frame relative to a free-running chip (measured +1 byte per frame at a one-byte-per-sample step, accumulating to dozens of bytes over the several hundred frames a pointer is polled). The figure of "about 32.604 kHz" quoted for this chip in the milestone statement agrees with that host-induced rate to 0.005 % and with no clock-derived value; this record could not independently retrieve the bulletin it comes from. The nominal rate (12.5 MHz / 384) shared by two independent implementations is used, and the +0.165 % is classified as a host artifact of the reference, not hardware.
2. **The M4/M5 reference driver never ran the PCM resynchronization at all.** `scd_oracle` runs `system_frame_scd()` without `audio_update()`, so `pcm.cycles` is never reset while the sub's cycle counter is rebased every frame: after the first frame the chip is never run again, and the pointers freeze (observed: the same byte at 3.5 million consecutive reads of the input-free route). Nothing before the first pointer read was affected (the pointers are unobservable until then), which is why M4/M5 are unchanged; but that driver is not a usable reference past F0.

Two private variants of the driver were therefore built for M6 (ignored directory, never committed): **A** the shipped behaviour (audio enabled each frame) and **F** ("free-running") the same chip code with the host's per-frame phase restart removed: the sample clock counts absolute sub cycles and is anchored at the chip reset. F is the reference for the pointer model; A is reported alongside as the quantified host artifact. Both log every PCM access (kind, chip offset, value, absolute cycle).

## Authentic baseline (M5's frozen program, runtime unchanged)

Inputs and routes exactly those of ADR 0227 (disc, BIOS, 8 KiB formatted backup RAM, pad schedule R1; entry-relative reference frames). No gameplay input was altered.

- **F0** (R0, input-free): the frozen program stops `pcm_unsupported` on the **sub** MC68000, a **byte read**, chip offset `$11` (the high byte of **channel 0**'s pointer, bus `$FF0023`), 49.0 M sub / 25.4 M main instructions retired, 23.5 s wall, 24 MiB peak. The reference (variant A or F) reaches the same read at entry+2169 frames and then polls it (about 4,700 reads per frame, 800 frames, the pointer advancing at about 2 pages per frame).
- **F1** (R1, the Checkpoint H script): `pcm_unsupported` on the **sub**, a **word read** at bus `$FF0038` = chip offset `$1C` (the low-byte register of **channel 6**), 247.6 M sub / 159.0 M main retired, 104.7 s wall, 26 MiB peak. It is the first half of a **32-bit read** (`$1C` then `$1D`: the low byte, then the high byte, each in the low lane of its word), executed once per frame; the reference reaches it at entry+12456 frames and reads the pair 44 times over 40 frames. Both reads are within the cost bound; both reproduce ADR 0230.
- All earlier M5 evidence (checkpoint frames, module identities) is unaffected: no PCM register was ever read before these stops.

## Specification (the decision)

The product models, per channel, the 27-bit running address and one chip-wide sample counter `samples` (events already applied), and nothing else. `scd_pcm_sync(m, t)` applies the events `origin + k x period < t` (a bounded loop; each event steps every running channel while the chip is enabled; the loop is skipped when no channel runs, because then only the counter moves). A state-changing PCM write and every pointer read synchronize to the access instant first. No second clock, thread, floating point value or scheduler is introduced. The pointer registers `$10-$1F` are served as in the table; everything else read is refused before any state is touched.

## Gate

`PCM_TIMING_FEASIBLE`: the sample clock, the phase/ordering rules and the readback are specified from two independent implementations and the reference's measured behaviour, and are testable against both (T004). Residual assumptions, each listed in the final report: (a) the grid anchor (reset instant) and the strict-before ordering at an equal instant are conventions (the chip is free-running; no source documents them); (b) the loop-marker step (GPGX) versus MAME; (c) the zero upper lane of a word read; (d) the open-bus value of an even-address byte read is not modelled.

## Evaluation rules and their history (stated plainly)

What was fixed before any generated program ran past F0: the chip specification above, the reference variants, the baseline reproduction and the requirement that the chip model equal the reference's chip code (a) on seeded synthetic operation sequences (T004) and (b) on the reference's own authentic operation sequences replayed through the product model, every pointer read equal. What was **not** fixed in advance: two exploratory generated-native runs of the corrected runtime (diagnostic builds made while the model was being implemented) were inspected before the acceptance rule for the *native* comparison was written. They showed identical executed PCM operation sequences but a one-sample difference of some pointer reads. The rule below was derived from that observation; it is therefore reported as post-hoc, and the conclusion rests mainly on (a) and (b), which do not depend on the two machines' CPU timelines:

1. A generated-native pointer read is compared with variant F by the number of sample events applied since the channel started. A difference is accepted only as CPU-timeline skew: the executed PCM operation sequences (kind, chip offset, written value) must be identical, and the measured skew of the two machines' instants must be shown to remain below one sample period over the interval for the read to differ by one event.
2. The model, the specification and the reference variant are not altered to obtain agreement; the M5 evidence is re-run unchanged on the final frozen program.
3. The next frontier is recorded, not implemented, unless it belongs to the pointer-state contract.
