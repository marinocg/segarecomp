# ADR 0290: Typed ROM edits with expected-value assertions, and per-revision symbols with address provenance

- Status: accepted (combined delivery F04: SEG-136-T001, SEG-136-T002).
- Builds on: ADR 0281 (schema 3), ADR 0288 (host implementation), ADR 0280 (adapters: ROM is immutable at runtime, edits are build-time), ADR 0289 (CLI, variant identity).

## Context

Schema 3 reserved the `rom-edit-set` payload kind and its informational `edits` count but did not define an entry. Game-specific patch-export scripts hard-code addresses and byte values per ROM revision. The milestone needs an official mechanism that is verifiable (a wrong address or an unexpected original byte must fail the build, never silently corrupt a ROM), deterministic across hosts, and revision-aware.

## Decisions

1. **Edit file format (`rom-edit-set` v1).** An ASCII text payload, LF-separated; blank lines and `#` comment lines are allowed; one edit per line with exactly five space-separated fields: `<revision|*> <type> <site> <expected> <value>`. Text, not a binary container, because a reviewer must be able to read what a package changes, and byte-order handling is then explicit in the type name rather than in host `struct` layout. `type` is `u8`, `u16`, `u32` (the platform's default order), `u16be`, `u16le`, `u32be`, `u32le` or `bytes`. Integers are `0x` plus exactly `2*width` lower-case hex digits; `bytes` is lower-case hex of equal even length for `expected` and `value`. Anything else (upper case, tabs, CR, non-ASCII, wrong digit count) is `E_EDIT_SYNTAX`; there is no tolerant parse, because ambiguity in a patch is a defect.
2. **Platform-correct endianness is a property of the adapter table, not of core code.** `Adapter::rom_big_endian` gives the default order of `u16`/`u32` (Genesis 68000 data: big; Master System Z80 data: little). The explicit `be`/`le` types express mixed data (for example Z80 code stored in a Genesis ROM). Values are converted to image byte order by shifting, never through host memory layout, so every host produces identical bytes. No alignment is enforced: a ROM edit is a build-time byte replacement, not a CPU access.
3. **Expected-value assertion.** `expected` is compared with the exact original image before anything is written; all assertions are evaluated before the first byte changes, so a mismatch yields no image at all (`E_EDIT_EXPECTED_MISMATCH`). The image must first be the exact image of one declared revision (selected by SHA-256, as everywhere in schema 3; `E_IMAGE_MISMATCH` otherwise). Diagnostics name the line and offset and never print image bytes.
4. **Revisions resolve independently.** An edit names one declared revision or `*`. For each declared revision the applicable edits (its own plus `*`) are resolved to byte ranges, sorted, and checked for overlap on their own: the same offsets in different revisions are not an overlap, a bad assertion for one revision does not affect another, and an overlap in one revision rejects the package. `*` asserts the same expected value against every revision it covers. Overlap (`E_EDIT_OVERLAP`) is any intersection of two ranges in one revision; adjacency is allowed. An edit beyond the largest supported image (16 MiB) is `E_EDIT_RANGE` at check time; one beyond the real image end is `E_EDIT_RANGE` at apply time.
5. **Checking happens at the reader.** `read_package` (and so `mod check`, `pack`, `build`, `inspect`) parses every `rom-edit-set` payload, verifies the informational `edits` count (`E_EDIT_COUNT`), and resolves symbols and overlap for every declared revision. A project computes the count itself; a stated `edits = N` must agree. Application is `apply_rom_edits`, used by `effective_image` (install/variant keying) and by `segarecomp mod apply <dir|package> --rom <image> --out <image>`; it composes with the existing combination rule (`rom-edit-set` never coexists with `bps-image`; guest code will follow it).
6. **Symbols.** A manifest gains the optional key `symbols`: an array of `{name, revision, address, provenance}` sorted strictly by `(name, revision)` (so packing is canonical and identity does not depend on the order in `mod.toml`). Names are tokens (`a-z 0-9 _ - .`, at most 64) so a symbol map cannot carry disassembly or prose; the address is an image offset below 0x01000000; the revision must be declared. `provenance` is `manual` (author-entered), `verified` or `imported-hint` (tool output). **Only `verified` entries resolve for an edit site.** A site `@name` or `@name+0xN` needs a `verified` entry for the revision it is resolved in: none at all is `E_SYMBOL_UNKNOWN`, a `manual` or `imported-hint` entry is `E_SYMBOL_NOT_VERIFIED`. Such a failure fails the build (`check`, `pack`, `build`) and the package reader. A repeated `(name, revision)` is `E_SYMBOL_DUPLICATE`, an undeclared revision `E_SYMBOL_REVISION`. This is an additive optional manifest key of schema 3 (a package without it is byte-identical to before; pinned identities are unchanged), and `symbols` participate in the content digest only when present because they decide where edits land. "Verified" is the author's classification; the check that makes it meaningful is the expected-original-value assertion every edit carries against the exact image.
7. **Hints are never promoted.** `segarecomp mod import-hints <dir> --revision <label> --from <file>` converts a symbol list (`name address` or CSV such as a Ghidra symbol-table export; `0x`/`$` hex or plain decimal; a bare zero-padded token is refused as ambiguous; names are folded to the token alphabet) into `imported-hint` `[[symbol]]` blocks appended to `mod.toml`. It never creates `verified`, never overwrites an existing entry, and a failed import changes nothing. Promotion is a deliberate edit by the author.
8. **`inspect`/`check` print the provenance** (`symbols` array) and the edit count (`rom_edits`) for both project and package.
9. **Template.** `init --template rom-edit` now writes a commented `edits/main.edits` and declares it as a source.

## Consequences

- New stable classes: `E_EDIT_SYNTAX`, `E_EDIT_REVISION`, `E_EDIT_COUNT`, `E_EDIT_OVERLAP`, `E_EDIT_RANGE`, `E_EDIT_EXPECTED_MISMATCH`, `E_SYMBOL_UNKNOWN`, `E_SYMBOL_NOT_VERIFIED`, `E_SYMBOL_DUPLICATE`, `E_SYMBOL_REVISION`, `E_SYMBOL_HINT` (import only).
- BPS construction from the edited image (T005) and guest-code injection (T004) are separate; edits are applied through `effective_image`, which currently yields digests, not a stored image.
- The edit text is deliberately not canonicalised: the payload digest covers the exact bytes; two textual spellings of the same edits are two packages.

Rejected: a binary edit container (opaque to review, host-layout hazards); making `manual` entries usable as sites (the milestone requires verification); a separate symbol payload kind (would reopen the closed kind table for data the manifest can carry); auto-promoting imported hints.
