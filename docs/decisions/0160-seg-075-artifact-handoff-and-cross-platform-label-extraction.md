# ADR 0160: SEG-075-T002 private-artifact handoff, reproducibility identity and cross-platform label extraction

- Status: Accepted. C1 (sections 1-4): private-artifact handoff and v2 identity. C2 (sections 5-9): canonical cross-platform corpus,
  54 samples from 7 programs, every qualified T001 program extracted or typed.
- Task: SEG-075-T002, the first task of the combined SEG-075 product PR (T002-T006, checkpoints C1-C7, harness full refinement of
  2026-10-19). SEG-074 records, contracts and compiled-code optimizations, the SEG-072/073 frozen records and the T001 frozen plan, records
  and manifest are unchanged.
- Scope: offline research tooling only. No production, emitter, validator, runtime, launcher, admission or default change.

## 1. C1: what T001's `verify` proves, and what it does not

T001's `segarecomp_xplat_qualify.py verify` recomputes the sanitized manifest from the private build *records* and compares identities,
classes, outcomes and output digests with the committed manifest. It proves that the records agree with the public evidence. It does not
prove that the private sources, build trees, listings, toolchain inputs or images still exist and are unmodified. C1 adds that second level
as a separate tool, `tools/segarecomp_xplat_handoff.py`. The two levels are reported separately and never conflated.

## 2. C1: physical audit and content-addressed handoff

`segarecomp_xplat_handoff.py audit` enumerates the artifacts the SEG-075 successors need. It rehashes every physical file and classifies
each required artifact as `PRESENT_AND_VERIFIED`, `PRESENT_BUT_CHANGED`, `REPRODUCIBLE_BUT_NOT_PRESERVED`, `MISSING_REBUILD_REQUIRED`,
`MISSING_UNRECOVERABLE` or `NOT_REQUIRED_FOR_SUCCESSOR`. Every present file records the basis it was verified against. The bases, strongest
first, are:

- `t001_record`: a declared output against the T001 record digest; run `b` only when T001 recorded the runs byte-identical.
- `t001_record_code`: run `b` of a declared output whose runs T001 recorded deterministic by loadable-code digest only (a PRG symbol table
  may differ), checked against the recorded `code_sha256`.
- `plan_sha256` / `plan_commit`: a toolchain input against the frozen plan's SHA-256; a checkout's HEAD against the plan's pinned commit.
- `git_blob`: every working-tree file of a pinned checkout against its committed blob id. Hashing goes through `git hash-object
  --stdin-paths`, so `.gitattributes` end-of-line filters apply; skip-worktree entries of the sparse archive pilot are excluded.
- `product_text`: a staged Dockerfile and the embedded helper scripts against the committed product text.
- `cross_run_identical`: a non-declared build file (listing, object, map) identical in both reproducibility runs.
- `image_id`: a Docker image against `toolchains.json`, read from the daemon and from the preserved archive's own config digests.
- `external_manifest`: the SEG-072 bundle against its own checksum files.
- `baseline`: no earlier independent evidence exists (logs, records, single-run files). The digest is the first integrity record. It
  detects future drift and makes no claim about past correctness.
- `cross_run_differs`: a build file whose two runs differ. For a file a successor needs it is `PRESENT_BUT_CHANGED`, a required problem.
  For any other by-product it is recorded as `PRESENT_UNVERIFIED` and is never counted as verified.

A build file is *required* only when it is a declared output or a successor intermediate of a required candidate (the listings, objects
and maps T002 consumes). Other by-products are preserved, but `NOT_REQUIRED_FOR_SUCCESSOR`. Every not-required entry keeps its underlying
verification result in a separate field, and the receipt counts them (`not_required_underlying`). Required candidates are the seven T001
programs usable without review plus the toolchain-infrastructure demos. The pre-tool exploratory trees of the T001 session
(`seg075/{src,build,tools,logs,scripts}`) are superseded by the qualified cache `seg075/q`; they are counted, not preserved. The GNU `as`
listings of compiler-generated assembly (toslibc, EmuTOS, neogeosdk) and the vasm listings of vbcc-emitted assembly (space-invaders) were
never generated by T001. They are `REPRODUCIBLE_BUT_NOT_PRESERVED`, and T002's truth recipes create them (section 5).

Every preserved file is stored as an independent read-only copy in a content-addressed store:
`<HARNESS_ROOT>/.cache/seg075-handoff/cas/sha256/<2>/<sha256>`. Identical files are stored once. Copies, not hardlinks, are a deliberate
choice: the T001 tool rewrites records, helpers and logs in place, and a hardlink would let such a rewrite silently replace the preserved
evidence. An existing object is re-hashed before reuse and replaced if it is corrupt. A deterministic manifest (`manifests/<label>.json` plus
`.sha256`) records, per entry, the logical path, group, required flag, status, underlying verification, basis, digest, size and origin. The
five toolchain images are archived with `docker save` (`images/segarecomp-xplat-toolchains.tar`, sharing the store object's inode).
`docker load` restores the recorded image ids, and `verify` checks them from the archive's own config digests.

`verify` checks the *store*:

- every object exists, has the recorded size and rehashes to the recorded digest;
- the manifest matches its digest file (a missing digest file fails);
- with `--receipt` / `--expect-sha256`, the manifest also matches the digest recorded in the committed receipt, so a manifest rewritten
  together with its digest file is caught;
- no entry originates in a task worktree;
- no required entry carries a changed or missing status. `audit` and `verify` share one problem list.

`--fresh-process` re-executes the tool isolated (`python3 -I`, cwd `/`, minimal environment). Verification needs only the store, and the
origin tree may be deleted; `--check-origin` additionally reports origin drift. `restore` writes independent copies by default, so a
restored cache can be rebuilt without touching the store; `--hardlink` is for read-only inspection only. The same tool's `add` command
snapshots later trees (T002 corpus, T003 snapshot, T004/T005 models) for the C7 handoff.

C1 result (`tools/segarecomp_xplat_handoff.c1_receipt.json`):

- 21,463 physical files and 3,924,105,211 bytes verified, with 0 required problems.
- Required entries: 4,953 `PRESENT_AND_VERIFIED` and 4 `REPRODUCIBLE_BUT_NOT_PRESERVED`.
- Not-required entries (16,546) underlying status: 16,454 verified, 44 run-to-run-differing by-products recorded as unverified (an
  EmuTOS static archive, generated headers and localisation temporaries), and 27 logs.
- Run `b` of 124 declared outputs was verified by T001 code digest.
- All 24 checkouts are at their pins and clean, and every required working file matches its committed blob.
- All five images match `toolchains.json` both in the daemon and in the 1.21 GB archive.
- No symlink leaves the cache or points into a worktree.
- The T001 recorded `verify` still passes.
- The fresh isolated-process verification, bound to the receipt digest, passes with no origin drift. The store objects, the live cache and
  a restored copy are distinct inodes (2.1 GB physical store after deduplication).
- Correction cycle 1, after independent review of `b9713d2`: the review found that the first store hardlinked the live files and that
  run-to-run-differing files were counted as verified. The store was rebuilt from copies under the semantics above.

## 3. C1: versioned v2 recipe identity

The T001 recipe hash (v1) covers the recipe, the candidate pin, the mount/shim/pilot and the plan's toolchain entry. It does not cover the
Dockerfile contents, the embedded helper scripts or the actual image. C1 adds a versioned v2 identity (`segarecomp_xplat_qualify.py
identity`, schema `segarecomp.xplat_qualify.recipe_identity.v2`). It contains:

- the frozen v1 digest, unchanged;
- the committed Dockerfile contents through the whole base chain, or the candidate's own Dockerfile for the context-candidate image;
- the embedded helper scripts;
- the recorded image id of the recipe's toolchain and of every base.

The T001 plan, records, manifest and v1 digests are not rewritten, and nothing claims that T001 used v2. The sanitized document
`tools/segarecomp_xplat_qualify.identity_v2.json` binds every recipe's v2 identity to its frozen v1 digest. `identity --check` reports drift
of Dockerfiles, helpers, images or recipes.

`verify` now takes its input from `--manifest`, with the committed manifest as the default. It rejects `--out` (an output option of
`report`/`identity`) and a missing manifest path, so the documented path is honoured.

New tests cover:

- recipe drift (v1 and v2 move);
- Dockerfile drift (v1 blind, v2 moves; base-chain propagation);
- helper and image-id drift;
- the `compare_manifests` recipe-hash and source-revision gaps;
- `verify` against a non-default manifest, through the real CLI.

The handoff tests cover:

- missing, corrupted and truncated outputs;
- changed link maps;
- incorrect source revisions;
- a modified checkout file;
- end-of-line-filtered files;
- drift of an input, a Dockerfile or a helper;
- worktree refusal;
- fresh-process verification and restore.

## 4. C1: toolchain stability

Two successful runs prove run-to-run determinism on this machine. They do not prove long-term rebuildability. Each toolchain is typed:

| toolchain | classes |
|---|---|
| tc-gnu | existing machine; environment-dependent (Ubuntu apt binutils/GNU `as` versions float on the digest-pinned base) |
| tc-elf | existing machine; pinned tool inputs (GCC 13.3 / binutils 2.42 tarballs by SHA-256, floating build host) |
| tc-vbcc | existing machine; pinned tool inputs |
| tc-a68k | existing machine; pinned tool inputs |
| tc-mint | existing machine; environment-dependent (PPA packages and "latest" vasm/vlink/agtools) |

The durable recovery path for every toolchain is the preserved image archive. Rebuilding from Dockerfiles is a fallback with the
reproducibility limits above, not a guarantee.

## 5. C2: where the labels come from

Labels come only from assembler/compiler listings that provably describe the qualified binaries:

- **Assembler programs (BattleIsleEditor A68K, amiga-realtime3d and HelloAmi vasm).** The listings of the qualified T001 run `a` are used
  directly. Their objects and executables are the T001-recorded outputs.
- **Compiler programs (toslibc and neogeosdk GCC 13.3, EmuTOS GCC 4.6.4 MiNT, space-invaders vbcc).** T001 never produced listings for
  these. `segarecomp_xplat_corpus.py truth` reruns each qualified recipe in a fresh copy of the pinned source, inside the same preserved
  offline image, with the assembler wrapped to also write a listing. A truth run is accepted only if every M68K object and every final
  image it produces is byte-identical to T001 run `a`. All seven truth runs were accepted (EmuTOS 4 configurations, toslibc, neogeosdk,
  space-invaders), so their listings describe the qualified objects.
- **GNU as listings need one more step.** GNU as loses its byte-to-line attribution after GCC's `#APP`/`#NO_APP` inline-assembly scrubbing
  toggles: bytes are printed one or more lines late. In EmuTOS this affected 73 of 188 objects. The wrapper therefore keeps GCC's
  assembly and re-assembles a copy with only those two marker lines removed. That listing is used only when the re-assembled object is
  byte-identical to the real one, which held for all 188 EmuTOS objects and every toslibc/neogeosdk object.
- **Residual desynchronization fails closed.** Bytes listed on a statement that cannot emit them (non-zero bytes on a directive or label
  line), or an instruction line without bytes, rejects the whole section to `U` (`LISTING_BYTE_LAG`). Zero fill on a section-changing
  directive is the m68k even-size section padding and is `U` (`SECTION_PADDING`).

## 6. C2: from listing rows to per-byte labels

1. **Row extents.** A row's extent is the distance to the next emitting row in its section. Its listed bytes must equal the assembled
   section bytes outside relocation fields (`LISTING_OBJECT_DISAGREE`, overlapping or out-of-section rows reject the section). A68K lists
   at most 12 bytes per row, so long data rows are compared as a prefix. An instruction row is labelled for exactly its listed bytes. A
   following unlisted gap is `U` (`UNLISTED_GAP`, e.g. vasm `cnop` padding).
2. **Placement.** An assembled section is placed in the final image only where its non-relocated bytes match at exactly one even position
   (anchored on its longest unmasked run, at least 8 unmasked bytes). Otherwise it is `PLACEMENT_AMBIGUOUS`, `SECTION_NOT_IN_IMAGE` (not
   linked), `SECTION_TOO_SHORT_TO_PLACE` or `PLACEMENT_OVERLAP`, and stays `U`. Without a separate object (vasm `-Fhunkexe`), listing
   section i is hunk i. Relocated fields are masked, so placement and labels are relocation-invariant (tested). Bytes not covered by a
   placed section (libgcc, ambiguous, unlisted) stay `U`.
3. **Row classes.** Instruction rows become `I` + `c`, data rows `D`, alignment/padding/macro/other emitting rows `U`.
4. **Decoder check (base MC68000).** Every placed `I` row is checked with the CPU-owned decoder (`segarecomp m68k-decode-token-report`,
   decoder sources of product `main` unchanged). It must decode as an ordinary instruction, or as the intended `ILLEGAL` form, of exactly
   the listed length. Otherwise it is typed `DECODER_REJECTED` / `EXCEPTION_FORM` / `LENGTH_MISMATCH` / `ODD_START` and becomes `U`. The
   MC68000's maximum instruction length is 5 words, so the token length is exact.
5. **Fall-through.** A data row reached by fall-through from a non-terminating instruction, and every contiguous data row after it up to
   the next instruction, becomes `U` (`DATA_AFTER_FALLTHROUGH`): inline arguments or encoded instructions.
6. **Encoded 68010+ opcodes.** A data row in an instruction-bearing section whose first word is a 68010+/coprocessor opcode (MOVEC, MOVES,
   RTD, BKPT, line-F coprocessor ids 0-3) becomes `U` (`D_ROW_ENCODED_NON_BASE_OPCODE`).

Rules 5 and 6 are how EmuTOS's guarded 68010+/68030/68040 code is filtered. It is written with cpp macros that emit `dc.l` words
(`MOVEC_*`, `PMOVE_*`), so it never appears as instruction rows. Source-text scanning (the T001 heuristic) plays no part.

What remains, as a disclosed upper bound: other data rows in instruction-bearing sections whose first word is not an ordinary decode stay
`D` (`D_ROW_NON_BASE_WORD_IN_CODE_SECTION`, e.g. 10,104 rows in EmuTOS, overwhelmingly tables and strings). An encoded non-base instruction
reachable only by a jump, and not starting with one of the listed opcode words, could hide among them. No such case is known.

## 7. C2: canonical samples

There is one sample per loadable image:

- PRG text+data;
- each Amiga hunk;
- a raw EmuTOS ROM;
- the Neo Geo ELF load image;
- the text segment of each object of the object-only space-invaders build.

The HelloAmi disk images (`.adf`) embed the other units and are excluded. Each sample has the SEG-072 registry layout (`image.bin`,
`classes.bin`, `tokens.bin`, `seeds.json`, `meta.json` with an `audit`), plus `relocs.json` (relocation fields as evidence, never
labels) and `spans.json` (typed findings).

Seeds are only independently established executable roots: the container entry (PRG and first CODE hunk offset 0, the EmuTOS reset
vector, the ELF entry). Object-only units have none. Symbol tables never create labels or seeds.

`meta.json` records platform, toolchain, workload class, CPU variant, truth provenance, digests and a provisional lineage (the candidate).
T003 assigns the real lineage groups. The unchanged SEG-072 loader (`segarecomp_ml_v3_train.Image`) loads all 54 samples (12,155
128-byte cells, 9,648 positive).

Extraction is deterministic. A second run into a different directory reproduces the corpus manifest digest
(`cc2a49188fef970050175a66533ba9e15d5cb92e55fc09d12fdb666d1728126e`) and every data file byte for byte. The end-to-end test repeats this
on a fixture.

## 9. C2: private artifacts and limits

- Private outputs live in `<HARNESS_ROOT>/.cache/seg075/t002/`: `truth/` (truth runs with listings, kept assembly, relist proofs) and
  `corpus/` (54 samples + `MANIFEST.json`).
- The handoff store manifest `c2-t002-corpus` extends `c1-t001-audit` with these trees and the exact decoder binary. Its receipt is
  `tools/segarecomp_xplat_handoff.c2_receipt.json` (fresh-process verify PASS, 0 required problems). The four C1
  `REPRODUCIBLE_BUT_NOT_PRESERVED` truth-listing entries are now preserved.
- The samples are dense in code: 79% of labelled cells are positive. Many images are smaller than M3-R's 32-cell (4 KB) training segment,
  so only images of at least 4 KB contribute M3-R training segments. This is a T003 design input.
- The raw numbers above are instruction starts, not independent diversity. EmuTOS's four configurations, BattleIsleEditor's six editors
  and amiga-realtime3d's nine incremental programs are each one lineage. T003 groups and deduplicates them.
