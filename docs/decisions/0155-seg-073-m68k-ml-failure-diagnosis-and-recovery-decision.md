# ADR 0155: SEG-073 M68K ML failure diagnosis and recovery decision

- Status: Accepted. **Selected hypothesis: H5 - stop further M68K ML model work; preserve production M3 + B35 with broad-AOT fallback.**
- Scope: offline research only, from the preserved SEG-072 artifacts. No model was trained, no cross-validation was rerun, and no SEG-072 record, label,
  one-shot marker, output or weight was modified. SEG-072's classification (`RECALL_FAILED`, ADR 0154) is final and unchanged; the one-shot
  `sealed` command was not rerun. Production M3 (`gen2`) + B35, Optimized v1, the structural prune, the validator, generated-native
  compilation, launchers, Sega CD hardware and runtime execution are unchanged.
- Tooling: `tools/segarecomp_ml_v3_diagnose.py` (`smoke`, `infer`, `analyze`); tests `tests/segarecomp_ml_v3_diagnose_test.py` (synthetic,
  standard library only). Aggregate results: `tools/segarecomp_ml_v3.diagnosis.json` (no addresses, cell indices, labels, bytes or per-cell
  values; private per-cell results stay in ignored storage).
- Evidence status: development numbers are leave-one-lineage-out out-of-fold (ADR 0153). Numbers on the five qualified sealed lineages are
  **exploratory**: those lineages were exposed by the SEG-072 one-shot run, so nothing here is blind evidence or a production-readiness claim.

`smoke` (with `SEG072_ROOT`/`SEG049_ROOT` pointed at the payload): **PASS** on the bundle directory, and **PASS** again on a copy extracted from

- reproduced the stored production-M3 scores **bit for bit** for one bundled SGDK image, one operator ROM and one Sonic CD module;
- reproduced every stored M3-R development table pair (B35/B45/B50/B60/ADAPT) exactly;

## 2. Sonic Spinball (E05): label credibility of the missed starts

The 40 frozen-pair misses sit in two 128-byte cells (18 + 22 starts, occupancy 0.28 / 0.34). They are not adjacent: one cell lies between
them, and that cell has 64 labelled starts and occupancy 1.0. M4-Dense's 134 misses at B50 are those two cells plus that middle cell and one
cell elsewhere in the image; at B35 it misses one more such cell. Every labelled code block (a maximal run of labelled instruction bytes) was
classified from evidence that **never uses a model score**:

- **Production root:** a direct-control-discovery root of the CPU-owned production decoder inside the block.
- **Independent disassembler:** a candidate from a genuinely independent tool inside the block. The tool was pinned headless Ghidra 12.1.2
  whole-ROM analysis (ADR 0025 recipe), which produced 8,312 code-entry candidates for E05.
- **Evidenced reference:** an IDA `CODE XREF` whose origin lies in another block that is itself supported by a root or a Ghidra candidate.
  References from unsupported blocks don't count, because branch-like words inside a table refer only to each other.
- **Flank-data signature:** the histogram intersection between the high-byte distribution of the block's instruction words and that of the
  labelled data words within 512 bytes on each side. Data that was read as code keeps the neighbouring table's signature.

| class | rule | E05 blocks | E05 starts |
|---|---|---|---|
| independently corroborated code | root inside, or Ghidra candidate + evidenced reference | 97 | 42,473 |
| plausible, not independently established | Ghidra candidate or evidenced reference, no data signature | 28 | 4,040 |
| evidence suggesting misclassified data | no root, no Ghidra candidate, no evidenced reference, signature >= 0.5 | **4** | **168** |
| unresolved | otherwise | 35 | 2,459 |

The signature threshold sits in an empty gap:

- Supported E05 blocks score at most 0.222.
- The four flagged blocks score 0.69-0.88.
- Negative control on development truth taken from source listings (14 Genesis images, 5,697 code blocks with adjacent data,
  374,638 starts): **0 blocks** reach 0.5. The highest-scoring rooted block reaches 0.263.

**Every missed cell of the frozen pair, and of M4-Dense at B50, is `DATA_EVIDENCE`.** None of these cells has a production root, a Ghidra
candidate or an evidenced reference. Their only references are short branches from neighbouring unsupported blocks, and they carry the
adjacent table's byte signature. The listing shows the same pattern: these "instructions" are register-to-itself moves and repeated
predecrement loads sitting between table rows of the same word shape. That matches the disassembly readme's warning that some data was
interpreted as code.

At B35 every model also misses 3 starts in `UNRESOLVED` blocks, reported as such:

- frozen M3: a sparse cell (occupancy 0.09);
- M3-R, and M4-Dense at B35/B45: three starts of an unresolved block that shares a cell with a `DATA_EVIDENCE` block.

Diagnostic credibility-adjusted sealed misses (E05 starts in `DATA_EVIDENCE` blocks excluded; SEG-072 labels and results unchanged):

| model | B35 | B45 | B50 |
|---|---|---|---|
| frozen M3 | 85 -> 3 | 0 -> 0 | 0 -> 0 |
| M3-R (frozen pair at B50) | 77 -> 3 | 40 -> 0 | **40 -> 0** |
| M4-Dense@128 | 171 -> 3 | 171 -> 3 | 134 -> 0 |
| M4-Dense@64 | 171 -> 3 | 143 -> 3 | 134 -> 0 |

E01, E03, E06 and E07 have no miss at any of these budgets for any model. **The decisive SEG-072 sealed failure is therefore best explained by
probable label noise in the IDA-derived truth, not by a demonstrated generalization failure of the model.** This explanation does not reopen
SEG-072: its rule pre-registered IDA instruction rows as confident labels, and `RECALL_FAILED` stands.

## 3. Model complementarity

Comparisons use one selection unit and one retained-byte budget for every model. Conversion from 64 B to 128 B is defined as the **max of
the two 64-byte cell scores**. M4-Dense's 64-byte cell score is already a max of word logits, so the converted M4@64 equals its native 128-byte
aggregation exactly; this holds on 50/50 development and 5/5 sealed images. In this section "M4@64" is therefore the same ranking as
M4@128, and M4@64's only difference is its finer selection unit (ADR 0153 tables).

"Hard" cells are non-seed positive cells outside some model's ranked budget:

| development, out-of-fold | B35 | B45 | B50 |
|---|---|---|---|
| hard cells (any model) | 347 | 36 | 4 |
| missed by every model (systematic) | 26 (D07 25, D01 1) | **0** | **0** |
| hard cells: frozen M3 / M1 / M3-R / M4 | 209 / 204 / 213 / 137 | 15 / 12 / 10 / 13 | 1 / 1 / 0 / 2 |
| each model's hard cells ranked inside the budget by another model | 183 / 178 / 187 / 111 | all | all |

What the hard cells are:

- **At B50:** four single 128-byte fragments (mean occupancy 0.035, each adjacent to a non-positive cell), spread across three lineages and
  three different models:
  - frozen M3: the documented Sonic CD Work RAM copy fragment;
  - M1-HGB: one Sonic 2 fragment;
  - M4-Dense: two Shining Force II fragments.
- **At B45:** 32 of the 36 hard cells are D07's.
- **At B35:** D07 dominates (324 of 347), and 25 D07 cells are missed by every model.

The failures are complementary at B45/B50 and systematic only for D07's dense code at B35. On the exposed sealed lineages, every hard cell at
B45/B50 is one of E05's `DATA_EVIDENCE` cells. Frozen M3 ranks them inside B45; M3-R ranks the fully "code-like" middle cell inside the budget
but the two partially "code-like" cells low, which is consistent with those cells being data.

## 4. Training exposure

The M3-R final-fit sampler was replayed exactly: `RandomState(49)`, 30 epochs, 32-cell segments, per-image random offset, and batches of 8
with the remainder dropped. The M4-Dense final-fit window sampler was replayed exactly for its three seeds (lineage-uniform, then image by
size, 2,048-word central windows).

| | M3-R actual | M4-Dense actual | hypothetical H1 schedule (not trained) |
|---|---|---|---|
| D01 share (39 of 50 images, one lineage) | **0.502** | 0.089 | 0.091 |
| D03 share | 0.286 | 0.092 | 0.091 |
| each homebrew lineage D05-D12 | 0.010-0.030 | 0.089-0.093 | 0.091 |
| positive share (dense / mixed / sparse) | 0.126 / 0.015 / 0.005 | 0.118 / 0.007 / 0.002 | 0.178 / 0.016 / 0.005 |
| SGDK runtime (masked) share | 0.031 | 0.163 | 0.184 |
| rare-fragment share of positive visits | 0.162 | 0.093 | 0.126 |
| images never exposed | 5 (tiny Sonic CD modules < 32 cells) | 1 | 5 |

Proportional segment sampling made two lineages take 79% of M3-R's exposure: D01 because 39 of the 50 images belong to it, and D03 because
Shining Force images are large. Corpus: 50 images; 12,921 dense / 1,572 mixed / 531 sparse positive cells; 83,204 negative cells; 3,243 masked
cells; 2,483 rare-fragment positive cells.

The hypothetical H1 schedule (lineage-uniform, segment start uniform within the lineage, segments holding a rare-fragment positive weighted
x3, same 3,121 segments per epoch) would balance lineages. It would also **lower** the visits of the four observed B50 hard development cells
to 0.59x, because they sit in D01/D03. It cannot reach the five sub-segment Sonic CD modules either, since that would need variable-length
segments; those modules are seed-covered anyway.

M4-Dense already samples lineages uniformly and still did not beat M3-R on development (D03) or on the sealed set (E05). No observed failure
class is addressed by lineage balancing. Improved recall from this schedule is **not claimed**: it was not trained.

## 5. Reinterpreting the old metrics

The original SEG-072 measurements are preserved unchanged in the record. Examples:

- M3_FROZEN+B35: 8,066 misses, mean retained 0.357, worst-lineage FRF 1.0.
- M3-R+B50: 0 misses, mean retained 0.505.

The diagnostic-only metrics below sit beside them:

- **Minimum required retained fraction:** |seeds ∪ positive cells| / cells, i.e. what a perfect ranking would still retain.
- **Required fraction:** seeds ∪ the shortest ranked prefix holding every non-seed positive.
- **Ranking excess:** required minus minimum.
- **Last uncovered positive rank:** the rank percentile of the worst non-seed positive cell.
- **Post-validator overhead:** from the stored K-stage results.

**D07 (240p Test Suite)** has 667 positive cells of 2,048 (32.6%), 28 seed cells and 6 seed-covered positives. B35 gives 717 ranked cells,
which is enough for the 661 non-seed positives, so **every B35 and B45 miss is a ranking failure, not a minimum-budget impossibility**.

The slack is thin, though. The minimum required fraction is 0.336, but the required fraction is 0.456 for M3-R and M4-Dense, 0.456 for M1 and
0.471 for frozen M3. That is a ranking excess of at least 0.119 for every model, against the 0.014 that complete recall at B35 would allow.
Missed D07 positive cells at B35: 198 frozen M3, 194 M1, 202 M3-R, 128 M4-Dense@128, 248 M4-Dense@64. Every model is complete at B50 because
B50 exceeds its required fraction.

**Degenerate worst-lineage FRF = 1.0.** Four tiny Sonic CD modules consist only of positive cells, so their FRF is 1.0 under any ranking,
yet all four are fully covered by mandatory seeds. Their minimum required fraction is also 1.0, and their ranking excess is 0. The seed-adjusted
last-positive rank does separate the candidates where FRF could not:

| | M3-R | M4-Dense@64 | M4-Dense@128 | M1-HGB | frozen M3 |
|---|---|---|---|---|---|
| worst image's last-positive rank | 0.455 (D07) | 0.477 | 0.608 (Shining Force II) | 0.815 | 0.939 (Sonic CD fragment) |

**Post-validator overhead** (stored K stage, broad-accepted Genesis development images):

| pair | mean K/U | admitted entries per labelled start | admitted entries that are not labelled starts |
|---|---|---|---|
| frozen M3 + B35 | 0.345 | 7.9 | 0.81 |
| M3-R + B50 | 0.437 | 8.3 | 0.83 |
| M4-Dense@64 + B50 | 0.475 | 10.2 | 0.84 |

The last column is an upper bound, because masked SGDK code counts as overhead. Whole-cell admission dominates generated-code size regardless
of the ranking model.

## 6. Cheap recovery experiments (no training)

**A - rank fusion** compares M3-R and M4-Dense with (1) the mean of the per-image normalized ranks and (2) reciprocal-rank fusion with k = 60
(fixed beforehand). All four use the same 128-byte cells, the same seeds and an identical ranked-byte budget. Development figures are
out-of-fold; misses / mean retained:

| method | B35 | B45 | B50 |
|---|---|---|---|
| M3-R | 8,121 / 0.357 | 435 / 0.456 | **0 / 0.505** |
| M4-Dense@128 | 5,603 / 0.357 | 511 / 0.456 | 2 / 0.505 |
| mean-rank fusion | 7,771 / 0.357 | 476 / 0.456 | 0 / 0.505 |
| RRF k = 60 | 7,631 / 0.357 | 476 / 0.456 | 0 / 0.505 |

Fusion reaches no complete pair below B50, is worse than M3-R at B45 (1 image), and is worse than M4-Dense alone at B35. On the exposed
sealed lineages it is worse than M3-R at every budget (B50: 104 vs 40 misses). **Rejected.**

**B - bounded structural expansion** of M3-R regions tests B1, filling single-cell holes, and B2, linear fall-through from production
direct-control roots using only the CPU-owned decode tokens (no target is invented, the ML score is never execution authority, the validator
is unchanged):

| | B35 | B45 | B50 |
|---|---|---|---|
| base | 8,121 / 0.357 | 435 / 0.456 | 0 / 0.505 |
| B2 direct flow | 8,121 / 0.357 (+128 bytes in total) | no change | no change |
| B1 gap fill | 7,229 / 0.371 | **78 / 0.473** | 0 / 0.524 |

B2 adds nothing: production root cells already cover their fall-through. B1 removes 82% of the B45 misses for +1.8 points of retention. It is
still incomplete (D07), and it adds about 2.1% of each image's broad-universe entries. At B50 it only adds cost. **Not a recovery.**

**C - sampling/objective feasibility.** All three options are unsupported by the observed failures:

- **Lineage-balanced M3:** no observed failure class is addressed (section 4).
- **Rare-fragment hard-positive sampling:** the B50 development hard cells are already handled by M3-R itself, and the sealed hard cells
  are probable data.
- **Boundary-aware multitask training (explicit instruction-start head):** would target boundary fragments that no longer limit M3-R. It
  does not address D07's whole-cell density ranking.

Estimated cost from SEG-072's recorded CPU measurements:

| hypothesis | estimate |
|---|---|
| H1 retraining | 11-fold cross-validation 12,930 CPU-s + final 574 s, about 3.8 CPU-hours (about 23 min wall on the 8-process farm, bounded by the slowest fold of 1,364 s) |
| H2 | M4-sized network, 33 fits x 868 s x 1.25 (assumed head overhead) + final: about 11 CPU-hours |

Both would need a fresh, untouched evaluation cohort before any claim.

## 7. Decision

| criterion | H1 balanced M3 | H2 multitask | H3 fusion | H4 expansion | H5 stop |
|---|---|---|---|---|---|
| causal fit | none: sealed miss is probable label noise; M4 is already balanced | weak: targets fragments M3-R already ranks | none: no recall gain below B50 | partial: gap fill helps B45 but stays incomplete | matches: no model-caused failure remains at B50; B35 failure is density ranking |
| recovers the failure class | not shown; hard-cell exposure falls | untested | measured no | measured no | n/a |
| other-lineage regression risk | high (D01/D03 de-weighted) | unknown | measured regressions | low | none |
| compilation economics | B50 already +15.3% generated C vs incumbent (ADR 0154) | same | same | +1.8-1.9 points of retention | incumbent preserved |
| engineering complexity | retrain + new cohort | new head, labels, cohort | small | small | none |
| fresh validation required | yes | yes | yes | yes | no |

**Selected: H5.** The causal analysis leaves no model failure for retraining or fusion to fix:

- The sealed failure lies in labelled starts that independent evidence classifies as probable data.
- The development misses at B45/B50 are complementary single fragments, and M3-R alone is already complete at B50.
- The remaining failure is D07-type dense code at B35/B45: a ranking failure, but one that would need every model to cut its ranking excess
  by roughly 8x (0.119 -> 0.014).

The economics gate needs a complete model near B35, which no cheap method reaches. The complete configurations (B50) already lose to the
incumbent by +15.3% generated C. Production keeps M3 + B35 with the validator and broad-AOT fallback; the dense image that B35 cannot cover
(D07) is already rejected by the validator and falls back to broad.

## 8. Recommendation and reopening conditions

No new ML training is recommended. Reopen M68K ML only if at least one of these holds; otherwise the next experiment is not worth its cost:

1. **The economics rule changes.** For example, a reliability-first policy accepts roughly B50 cost, or broad AOT becomes the cost baseline
   instead of M3 + B35. Then the cheapest experiment is a **pre-registered fresh-cohort evaluation of the existing frozen M3-R + B50, with no
   retraining**. Cost: inference seconds per image, plus about 15 minutes per lineage to rebuild/qualify truth (ADR 0152 procedures).
2. **A ranking change is proposed that targets dense-code images specifically.** It must first show, out-of-fold on development, a D07 ranking
   excess at or below about 0.03 before any sealed use. Budget for H1-sized training: about 3.8 CPU-hours per cross-validation.

Prerequisites for any reopened protocol:

- at least 7 newly selected, independently qualified, genuinely untouched lineages (E01/E03/E05/E06/E07 are exposed);
- a **pre-registered label-credibility screen** applied to disassembly-derived truth **before sealing**: the `DATA_EVIDENCE` rule of
  section 2, using a production root, an independent disassembler, evidenced references and the flank signature with threshold 0.5. Its
  outcome masks rows instead of counting them as confident starts;
- the diagnostic metrics of section 5 reported alongside the pre-registered ones.

## Reproduction

The private interpreter is the SEG-072 research environment. Outputs go to ignored storage.

```sh
<H>/.cache/seg049/venv/bin/python tools/segarecomp_ml_v3_handoff.py verify --bundle <H>/.cache/seg072-handoff/bundle-v1
<H>/.cache/seg049/venv/bin/python tools/segarecomp_ml_v3_diagnose.py smoke --bundle <bundle> [--rebase OLD=NEW]
<H>/.cache/seg049/venv/bin/python tools/segarecomp_ml_v3_diagnose.py infer --bundle <bundle> --out <ignored dir>
python3 tools/ghidra.py analyze --rom <E05 image> --output <ignored dir>/e05.candidates.json
<H>/.cache/seg049/venv/bin/python tools/segarecomp_ml_v3_diagnose.py analyze --bundle <bundle> --out <ignored dir> \
    --independent E05=<ignored dir>/e05.candidates.json --ida-listing E05=<private IDA text listing> --public tools/segarecomp_ml_v3.diagnosis.json
```

Ghidra's runtime input directory on this host was `0700` and unreadable to the container user. The analysis therefore ran with the same pinned
recipe, staged from a container-readable ignored scratch directory that was deleted afterwards; the tool itself was not changed. The IDA text
listing comes from the private sealed build tree; it is not bundled.

## Limitations

- **The `DATA_EVIDENCE` threshold was set after viewing the E05 distribution.** It lies in an empty gap (0.222 vs 0.687) and has no false
  flags on development listings, but it is exploratory, and it classifies evidence, not ground truth. No row was relabelled.
- The independent disassembler covers 89% of E05's labelled starts by block. The 35 `UNRESOLVED` blocks (2,459 starts) are neither
  confirmed nor refuted.
- Sealed results are exploratory (exposed lineages). M1-HGB has no final model, so it is absent from sealed comparisons. The hypothetical
  schedule's exposure is an expectation, not a training result. Training-cost estimates for H2 include an assumed overhead factor.
