# ADR 0312: virtual-sprite priority in the extension columns (producer-recorded winner classes)

- Status: accepted (W04). Supersedes Decision 2 of [ADR 0307](0307-virtual-sprites-in-the-widescreen-side-columns.md) (the "no class exists in a margin" rule); everything else in ADR 0307 stands. No change to the mod ABI, the guest, the VDP status, save states or the native picture. No game-specific behavior.

## Context

A `BETWEEN` virtual sprite is ordered against the native priority classes (above low-priority content, below high-priority content) and `BEHIND_PLANES` against the backdrop. Inside the picture the compositor reads the class of every pixel from the VDP's own side data (`GenesisVdpFrameAux::layer`). The extension columns are produced by the same VDP rules (plane A/B, window, optionally the frame's own sprites) from the frame's raster state, but only their colour was kept, so ADR 0307 rejected any `BETWEEN` / `BEHIND_PLANES` command that reached a margin (`GENESIS_VSPRITE_REJ_SIDE_PRIORITY`). A provider therefore had to use `ABOVE_ALL` for an actor beside the picture, which ignores a high-priority plane that the native game draws in front of it (a level whose water is a high-priority plane with transparent openings shows its low-priority enemies behind the water in the picture and solid in the margin).

## Decision

1. **The producer records the winner class of every extension pixel it produces.** `genesis_vdp_select_cram_index()` already decides which candidate gives a pixel its colour (the six-layer order: sprite-high, plane A/window-high, plane B-high, sprite-low, plane A/window-low, plane B-low, backdrop) and reports the winner's class; the extension producer now stores that value (`GENESIS_VDP_LAYER_BACKDROP` 0, `LOW` 1, `HIGH` 2) instead of discarding it. A transparent pixel of a high-priority tile is not a candidate, so the class is that of whatever lies below it. The class is the class of the candidate that actually colours the pixel; it is never derived from the colour, from neighbouring native pixels or from any other guess.
2. **Representation.** `GenesisFrameExtension::classes` is an optional, adapter-owned, preallocated byte buffer with `classes_capacity`: one byte per surface pixel, `(native width + 2 * side) x native height`, row-major like `pixels`. Only the extension columns are written (the picture columns keep using `GenesisVdpFrameAux::layer`). It is written in the same producer call, from the same per-line state, as `pixels`, so it describes exactly that frame. NULL or too small means no class data and nothing else changes (colours, status and flags are identical with or without it).
3. **Hand-over.** The producer passes the buffer to the adapter's `vsprite_compose` callback (new `classes` parameter, NULL unless the whole surface fits) while the frame's state is valid; the callback forwards it as `GenesisVirtualSpriteSurface::layer`. The buffer is never kept for another frame: it is rewritten every production, and a production that fails never calls the compositor.
4. **Composition.** In an extension column the compositor reads the recorded class of that pixel; all other rules are unchanged (`ABOVE_ALL` always draws, `BETWEEN` is hidden only where a high-priority pixel won, `BEHIND_PLANES` draws only where the backdrop won; layers are visited high to low and the first command that can draw a pixel claims it; clipping, provenance, frame verification, budgets and the visible-column limit are untouched). Hardware sprites of the extension (Level 3) and provider-authored scenery are classified by the same selector: an authored scenery word contributes its own priority bit and pattern transparency, so its class is the provider's own claim about its scenery, exactly as its colour is.
5. **Fail closed.** If a command that needs a class reaches a presented extension column and there is no class data (NULL or too small buffer), or a presented extension pixel holds a value that is not a class, the whole set is rejected with `GENESIS_VSPRITE_REJ_SIDE_PRIORITY` (13) and nothing is drawn, as in ADR 0307. The consistency scan covers only the columns the host presents and only runs when such a command exists, so `ABOVE_ALL` sets and picture-only sets cost nothing.

## Why this is the native behavior

The class is produced by the same selector that produces the pixel's colour, over the same candidates the VDP rules define, so for any pixel the recorded class is by construction the one the six-layer order assigns. In the picture the compositor already uses the VDP's own classes (`GenesisVdpFrameAux`), so a sprite crossing the picture boundary is ordered by one rule on both sides: where the plane is a transparent opening the sprite shows, where the high-priority plane is opaque it stays behind, without a seam. `ABOVE_ALL` output is byte-identical to before.

## Consequences

- One optional buffer and one callback parameter (internal producer/adapter contract, not the mod ABI); the Genesis viewer owns a static `(max width + 2 * max side) x max height` byte buffer.
- A provider may now submit `BETWEEN` / `BEHIND_PLANES` commands anywhere in the presented surface. A provider that wants a sprite to sit behind a high-priority plane the way the hardware does reads the priority bit of the piece (bit 15 of the sprite attribute word) and submits `BETWEEN` for priority 0 and `ABOVE_ALL` for priority 1.
- Tests: `tests/genesis_vsprite_priority_test.cpp` (hand-built scene driven through the real producer, a fake provider and the adapter callback, against an independent model of the documented rules: transparent openings, `BETWEEN` and `BEHIND_PLANES` in both margins, `ABOVE_ALL`, mixed sets, picture/margin boundary continuity, hardware-sprite candidates and ordering, fail-closed cases, replay and restore, stale buffers); `tests/genesis_extension_test.cpp` (the recorded class of every extension pixel against the six-layer reference over its randomized scenes, and the picture columns left untouched); `tests/genesis_vsprite_wide_test.cpp` (no class data keeps the ADR 0307 rejection); the viewer-level `tests/mod_vsprite_wide_test.py` and `tests/mod_vsprite_abi2_test.py` with their golden model (`tests/vsprite_model.py`).
