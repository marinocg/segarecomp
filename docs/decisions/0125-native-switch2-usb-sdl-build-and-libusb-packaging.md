# ADR 0125: Native Nintendo Switch 2 Pro Controller over USB: pinned SDL build with libusb, shipped as a separate DLL

- Status: Accepted. Scope: packaging and diagnostics only. No controller protocol, virtual controller, Steam API or driver installer is added.
- Related: ADR 0120 (shared SDL3 viewer foundation), `docs/testing/input-diagnostics.md` (evidence, support matrix and the physical test).

## Context

A Windows user's Switch 2 Pro Controller (`057e:2069`) works through Steam Input but Segarecomp saw only a raw joystick (state B). The Windows package shipped the official
`SDL3.dll` 3.4.16, which contains no Switch 2 driver. SDL 3.4.16's driver (`SDL_hidapi_switch2.c`) is USB-only (Bluetooth: "not supported", upstream issue 15963), is compiled only when
SDL is configured with libusb, claims USB interface 1 through libusb and sends the initialisation protocol itself, so Segarecomp must not copy it.

## Decision

1. Build SDL 3.4.16 from the SHA-256-pinned source tarball on every OS with `packaging/build-sdl3.sh`. On Windows (cl, static CRT) the launcher links the resulting `SDL3.lib`; the bundled
   Zig links `libSDL3.dll.a` generated by `zig dlltool` from the exports of the same `SDL3.dll`.
2. libusb 1.0.29 (pinned, verified): configure SDL with the full path of the official Visual C++ import library (header + lib), **load libusb lazily by name**
   (`SDL_LIBUSB_DYNAMIC "libusb-1.0.dll"`), and ship the official **MinGW** `libusb-1.0.dll` as a separate, unmodified DLL beside the launcher and in `sdl3/lib` (the PATH directory used for
   generated games). Static linking was rejected: it would place LGPL-2.1 code in SDL3.dll and require relinkable objects. The MinGW build was chosen because the Visual C++ build needs
   `VCRUNTIME140.dll`. The license text and the corresponding source archive ship in `licenses/`.
3. Gates fail the build instead of shipping silently without the driver: configure-time (`HAVE_LIBUSB`, lazy libusb name), a negative control (the same recipe with libusb disabled must fail),
   post-build literals of the driver in the binary (several independent ones, never the hint name alone), and for Windows `packaging/sdl_check.py windows` (x86-64, lazy libusb, SDL's libusb
   lookups against the shipped DLL, import-library/export parity, no redistributable runtime) run on the **extracted** package, whose DLLs must also be byte-identical to the built ones.
4. The build appends `(segarecomp-switch2-usb)` to `SDL_GetRevision()` only after the gate passed; the input diagnostics read it to separate "driver missing from this SDL" from libusb, Bluetooth,
   USB-interface and open failures. It is a declaration, not run-time proof, and says so.
5. SDL stays at 3.4.16: 3.4.18 and `main` have a byte-identical Switch 2 driver with the same Bluetooth `FIXME`. Bluetooth is documented as unsupported; there is no Segarecomp Bluetooth decoder.

## Consequences

* Verified in CI: the driver is compiled in; the packaged libusb resolves from the extracted package for the launcher and generated Genesis and Master System games; import libraries match.
* **Not verified, and not claimed:** that Windows binds WinUSB to the controller's interface 1 so libusb can claim it, that the controller initialises, and any physical input. If Windows does not bind
  WinUSB, the diagnostics say so ("USB interface not claimed") and the only remedy (a manual driver replacement) is deliberately out of scope: no Zadig, ViGEmBus, HidHide, service, administrator rights
  or automatic driver replacement. Steam Input compatibility is unchanged.
* The Windows package grows by the libusb DLL (~230 KB) and its source archive (~650 KB).
